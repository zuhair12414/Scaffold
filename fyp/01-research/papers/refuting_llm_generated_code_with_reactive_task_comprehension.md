## Abstract
Large Language Models (LLMs) for code generation have improved to the point where they are being integrated into professional software development workflows. Since these models occasionally generate buggy code, it is important for students to develop the ability to refute such code (typically, by identifying a counterexample input on which the code fails to perform the desired task). To create counterexamples manually, prior work has suggested code comprehension and task comprehension as two necessary skills. In this paper, we anticipate advances in software development tools and consider a limited form of the latter skill—reactive task comprehension—where students only need to correctly state the code's desired behavior on inputs suggested by an automated system. We make two contributions. First, we demonstrate the feasibility of such a system based on existing LLMs and code coverage tools. Second, we show that reactive task comprehension is surprisingly effective in refuting LLM-generated buggy Python functions in the HumanEval+ dataset. Bearing in mind that students are likely to have access to increasingly sophisticated code generation models and assistive systems, we discuss the implications of our findings for introductory programming education.

## 1 Introduction
To prepare students for a world where Generative AI tools are being rapidly integrated into professional software development [20], what skills should programming courses develop? Both educators and professional software developers agree that the code generated by the Large Language Models (LLMs) powering these tools, while plausible, cannot be trusted: it must be read carefully before it can be accepted [51]. Refute problems [39] have been suggested as one way to help students develop the ability to read code with a critical eye [40]. A Refute problem presents students with buggy code for a given task and asks for an input on which the code is incorrect (relative to that task). Agarwal et al. [2] assert that solving a Refute problem "requires students to comprehend buggy code well enough to recognize a mismatch with the stated task" (emphasis added). While this assertion may be true when manually refuting code generated by novices [2], we question whether it is true for LLM-generated code, and when assistive systems are available.

The motivation for our questioning is not to develop a user-friendly assistive system but to better understand the skills that students may (and may not) need to develop when such systems become readily available. Using a prototype system, we demonstrate a surprisingly effective way to refute LLM-generated buggy code that does not require students to comprehend the code, and requires them to comprehend the task only in a limited sense. More precisely, our assistive system generates a set of inputs and asks students to specify the code's expected behavior on those given inputs. We call this *reactive task comprehension*, to distinguish it from a deeper (*proactive*) form that is necessary to manually write high-quality test cases (see Section 2.1).

We attempt to refute buggy solutions generated by six LLMs for the 164 problems in the HumanEval dataset [14]. The task in each problem is to implement a simple Python function. To demonstrate how effective perfect reactive task comprehension can be, we use a canonical solution in place of students *only* to compute the function's expected behavior on inputs suggested by our system. Our research question is:

> **RQ:** In conjunction with our assistive system, how effective is perfect reactive task comprehension for refuting buggy code generated by LLMs?

For inputs suggested by our prototype system, perfect reactive task comprehension can refute over 99.95% of LLM-generated buggy solutions to HumanEval problems. This rather surprising result may spur efforts to develop assistive systems more capable than ours, including systems that seek clarity on a smaller set of well-chosen inputs. Instead of optimizing for such criteria, we discuss the pedagogical implications of our findings. For both Computer Science (CS) majors and non-majors, our study highlights the importance of developing reactive task comprehension skills. For CS majors, it also highlights the importance of detecting ambiguities in task specifications [22] and, echoing Agarwal et al. [2], recognizing subtle mismatches between the specification and the code.

## 2 Related Work

### 2.1 Reactive vs. Proactive Task Comprehension
Students often struggle to comprehend programming tasks [44, 52, 53], particularly when they have limited fluency in the language of instruction [1]. Researchers have developed pedagogical strategies to help students comprehend tasks by writing test cases before writing code [19, 23, 49, 52, 65].$^1$ In the approaches proposed by Craig et al. [19] and Denny et al. [23], students are asked to demonstrate task comprehension by specifying the code's desired behavior on a given test input. We call this shallow form of task comprehension *reactive*. Wrenn and Krishnamurthi additionally seek to develop a deeper (*proactive*) form of task comprehension by checking if student test cases are thorough—i.e., if every buggy implementation$^2$ fails at least one of these tests [65]. Liu et al. [43] noted the poor thoroughness of test cases in the original HumanEval dataset$^3$ and proposed HumanEval+$^4$. First, using type-aware mutations [64], they created a more thorough set of test cases to rigorously evaluate LLM-generated code. Second, they provided solutions to each of the 164 problems in the HumanEval dataset generated by 14 models.$^5$ Third, they maintain a leaderboard that evaluates the correctness of code-generation models using their rigorous test cases.$^6$

To write thorough tests manually, students must proactively consider a variety of inputs. Beginners often fail to consider inputs that are conceptually interesting relative to the task while writing test cases [5, 11]. Instead, they tend to focus on inputs corresponding to happy paths in their implementations [7, 11, 27]. Courses on software testing can reinforce an "implementation first" mindset by evaluating test case quality based on branch coverage or mutation analysis (e.g., [17, 36]). Doorn et al. observed the "implementation first" mindset among graduate students even when no implementation is provided, resulting in test cases that inadequately covered the input space [25]. This mindset is also prevalent among software developers [6], and tools such as CrossHair, based on symbolic execution [12, 63], assist developers by suggesting test inputs to maximize coverage.$^7$ To counteract this mindset, Shin and Kazerouni [58] encourage a "requirements-first" approach to manual test development that requires proactive task comprehension. This skill can be under-developed, even among professional developers [47]. Cordova et al. [18] and Wrenn et al. [65, 66] have developed tools to help students strengthen both forms of task comprehension.

### 2.2 Code Writing, Comprehension, Critique
The initial emphasis in many introductory programming courses is on understanding syntax and writing small programs [3, 45]. Since students now have easy access to code-generation tools, Becker et al. have identified an urgent "need to review our educational practices in the light of these new technologies" [9]. The recent ACM/IEEE-CS/AAAI CS2023 curriculum [38] suggests that "reading programs will see a sharpened focus and the idea of learning to program by writing, and reliance on learning syntax, will change towards learning to program by prompting, comprehending, verifying, editing, modifying, adapting, and testing code". Xie et al.'s theory of programming instruction states that students should learn to comprehend code before they are asked to write it [10]. A rich collection of learning activities and pedagogical approaches have been proposed to help students comprehend code [32].

In recent surveys, faculty interviewed by Lau and Guo [41] as well as faculty and developers interviewed by Prather et al. [51] emphasized that students must develop the ability to critique code (including LLM-generated code). Ziegler et al. showed that experienced software developers can rapidly critique LLM-generated suggestions. On average, they rejected over 70% of suggestions made by early versions of GitHub Copilot, but nevertheless demonstrated some gains in productivity [70]. Perhaps this is unsurprising, since software developers often spend more time on comprehending and critiquing code written by other developers rather than on writing code themselves [32, 60].

Similarly, Agarwal et al. suggest that Refute problems based on buggy code written by novices can help students develop the ability to critique code [2]. Refute problems differ from debugging, where a failing test input is often provided [46]. In contrast, to solve a Refute problem, students must discover a suitable input on their own and verify that the code fails (relative to the task) on that input. Agarwal et al. note that if students find such an input by pure guesswork, they would then only need reactive task comprehension and code tracing (a limited form of code comprehension [32]) to successfully refute the given code. However, to solve Refute problems effectively, they posit that a deeper form of code comprehension (at least at the Blocks and Purpose levels in the Block Model [57]) is necessary [2]. In contrast, our work shows that an automated system for generating test inputs can help students with strong reactive task comprehension skills to refute buggy LLM-generated code without requiring them to comprehend it.

### 2.3 Assistive Systems for Programming
Terms such as "LLM" and "model" have garnered much attention, and several papers cite the performance of "models" on code-writing benchmarks such as HumanEval [14]. This is misleading because, as Khattab et al. argue, such models cannot be used nakedly. To be useful, they must be components (albeit critical components) within larger systems that determine, among other things, precisely how these models are prompted [37]. The complexity of code-generation systems is advancing rapidly (see Jin et al. [34] for a recent survey), and we anticipate that students will continue to have easy access to these powerful systems. Further, we expect at least some introductory programming courses will encourage students to use such systems [61]. Motivations for early exposure to such systems include a desire to provide guided exposure to these powerful tools [41], and to reach a broader set of learners [15, 31, 62].

Developers are increasingly using such systems to write high-quality test cases [4, 20], leveraging LLMs' understanding of natural language for proactive task comprehension. However, developers remain wary of errors in AI-generated artifacts [51]. These errors can include tests with illegal arguments, as well as invalid tests.$^8$ In many cases, a precise structural definition of legal arguments is available. As LLMs improve in generating structured output [8], the former concern should subside. However, the latter concern is significant: LLMs are weak at reactive task comprehension [4]. Yuan et al. manually checked all failures caused by ChatGPT-generated tests and discovered that the cause in 85.5% of these was because ChatGPT misunderstood the expected behavior [67]. Many efforts are focused on reducing such errors [42, 69], but oversight by humans skilled in reactive task comprehension is likely to be necessary. This is in part true because tasks are often specified by non-programmers in natural language, and are therefore ambiguous [30]. Since our study seeks to understand the effectiveness of perfect reactive task comprehension in refuting LLM-generated code, we invoke the HumanEval+ canonical solution to accurately determine the expected behavior on inputs generated by our assistive system.

## 3 Methods

### 3.1 Our Assistive System
To refute a given implementation of a Python function, our system requires type-hints for all arguments.$^9$ Argument type-hints are missing in many of the HumanEval+ canonical solutions, but Liu et al. have specified the intended argument types via additional `assert` statements [43]. Based on these, we manually add argument type-hints when needed, as illustrated in Figure 1. The docstring in this example is grammatically poor, but for consistency, we do not modify the given docstrings.

```

----------------------------------------------------------------------------------------
Step 1. HumanEval+ model solution:
def strange_sort_list(lst):
    '''
    Given list of integers, return list in strange order ...
    '''
    assert type(lst) == list
    assert all(type(x) == int for x in lst)
    sorted_list = sorted(lst)
    ans, i, j = [], 0, len(sorted_list) - 1
    while i < j:
        ans.append(sorted_list[i])
        ans.append(sorted_list[j])
        i += 1
        j -= 1
    if i == j: ans.append(sorted_list[i])
    return ans

We create $T_1$ (Step 3) using $\text{LLM}(\text{task})$ and, after prepending the task to each LLM-generated solution, we create $T_2$ (Step 4) and $T_3$ (Step 5). Our system generates up to three sets of test inputs: $T_1$, $T_2$, and $T_3$. To simulate perfect reactive task comprehension, we use the HumanEval+ canonical solution to generate the desired output for each test input. For sets $T_1$ and $T_3$, inputs are generated using LLMs, which we refer to as $\text{LLM}(\text{task})$ and $\text{LLM}(\text{task} + \text{code})$ respectively. While these can be different models, we use Meta's Llama 3.1 model with 405 billion parameters in both cases. We use $\text{LLM}(\text{task})$ to generate inputs for $T_1$ based solely on the task, that is, the function signature and the docstring (see Figure 1). This model simulates proactive task comprehension to generate test inputs using the prompt shown in Table 1 (left).

Note that test inputs $T_1$ are generated once for each HumanEval problem and are executed against all buggy solutions for that problem. For implementations that behave identically to the canonical solution on all inputs in $T_1$, we generate additional inputs ($T_2$) using CrossHair$^{10}$. We provide this tool with both the task and the LLM-generated code (but not the canonical solution). Since CrossHair does not perform natural language processing, this tool simulates an "implementation first" mindset to generate test inputs. For solutions that behave identically to the canonical solution on all $T_2$ inputs, we use $\text{LLM}(\text{task} + \text{code})$ with the prompt shown in Table 1 (right) to generate a final set of test inputs $T_3$ based on both task and code comprehension. Our system fails to refute buggy solutions that behave identically to the canonical solution on all tests in sets $T_1$, $T_2$, and $T_3$.

### 4.1 The Two Failures
Our assistive system failed to refute just two of the 4,622 unique buggy solutions. Both these solutions were generated by GPT-4, for which we have exactly one solution per HumanEval problem.

For Problem 141, the task is to check whether a given string `file_name` is valid according to several criteria, one of which is that the string "starts with a letter from the latin alphapet ('a'-'z' and 'A'-'Z')".$^{14}$ GPT-4's solution differs from the canonical solution on the HumanEval+ test input `"éxample.exe"`. The canonical solution uses the `isalpha()` method which accepts the leading letter `é` (e-acute), whereas GPT-4's solution uses the regular expression `^[a-zA-Z]` which rejects this letter. Relative to the given task, GPT-4's solution is arguably correct. However, as discussed in Section 5.3, we treat this as a failure of our assistive system.

For Problem 144 (see Figure 3), the task is to check whether the product of two fractions (expressed as strings) is an integer. GPT-4's solution converts both fractions into floats and multiplies them (both these steps can lead to loss of precision) before invoking the `is_integer()` method on the resulting float. In contrast, the canonical solution extracts the numerators and denominators of the two fractions as ints, separately multiplies the numerators and denominators, and checks if the latter is a factor of the former (all steps leverage Python's arbitrary precision int arithmetic). The HumanEval+ tests include inputs that expose this loss of precision in GPT-4's solution$^{15}$, whereas our system fails to do so.

## 5 Discussion

### 5.1 Limitations and Future Work
Before considering the implications of our results, we first discuss the key limitations of our method. Since our work seeks to understand the impact of anticipated systems more powerful than our prototype, we note that these limitations may be less significant for those future systems. These limitations also suggest clear directions for future work.

First, in an attempt to ensure that our findings are generalizable, we have considered a range of code-generation models (Table 2). However, having considered only six models, and only the code produced by Liu et al.'s prompting strategy [43], our findings may not generalize well. Nevertheless, we believe that they are startling enough to warrant further attention.

Second, we have considered code of just one type (simple functions) in just one language (Python), from just one benchmark (HumanEval, which was released in 2021). Jain et al. have raised concerns that code generation models trained subsequent to this release may be contaminated with solutions to HumanEval problems [33]. To ensure that we are not overstating the efficacy of perfect reactive task comprehension, our study should be replicated on richer, "contamination free" benchmarks such as theirs.

Third, we filter out all solutions that pass HumanEval+ test cases on the assumption that these tests are thorough enough to detect all bugs. However, some LLM-generated solutions that pass these tests could be subtly buggy, and our approach may be unable to refute such implementations. A study by Singhal and Kumar noted several lacunae in an earlier version of HumanEval+ tests [59], but subsequent revisions have addressed those issues$^{16}$. Nevertheless, we acknowledge the limitations of this assumption.

Fourth, we have assumed that all buggy solutions that fail a common subset of HumanEval+ test cases are functionally equivalent. However, when two implementations are functionally equivalent but syntactically different, CrossHair may produce test inputs of different quality. We made this assumption to reduce the cost (in terms of time and money) of generating the additional test inputs $T_2$ and $T_3$. (Recall that while $T_1$ tests are generated once per problem, $T_2$ and $T_3$ tests are generated per buggy instance.)

### 5.2 Implications for Non-CS Majors
Our prototype can easily be integrated into a system that generates multiple (hidden) implementations for a given task and then asks a human a short series of questions of the form: "What should the code do on input $x$?" (where the system generates $x$). Our findings suggest that answers provided by a human with perfect reactive task comprehension can be used to eliminate (almost) all hidden implementations that are buggy. Hence, when the system reveals an implementation that survives elimination, this human can place substantial trust in that code without comprehending it. This aligns with the well-known AI researcher François Chollet's prediction [16]: "[P]rogramming from input-output pairs will be a widespread programming paradigm in the future, and that [paradigm] will be accessible to anyone". Such a paradigm may empower a broad community of non-CS majors who are interested in leveraging computing without necessarily developing a deep understanding of programming. For these learners, our findings highlight the importance of developing reactive task comprehension skills.

### 5.3 Implications for CS Majors
While CS majors will also benefit from developing reactive task comprehension skills, the instances where our assistive system fails to refute code generated by GPT-4 (Section 4.1) illustrate two additional skills that these learners must develop: (1) detecting ambiguities in task specifications, and (2) comprehending the code well enough to recognize potential mismatches with the task.

For Problem 141, while one can argue that GPT-4's solution aligns more closely with the wording of the task, it is possible that the author of that task meant to include diacritics$^{17}$. Since natural language is often ambiguous, Schneider argued that introductory programming courses should expose CS students to ambiguous task specifications [56]. One way to provide such exposure is via Probeable Problems [48], which encourage CS students to ask clarifying questions before coding [22].

The subtle error in GPT-4's solution to Problem 144 (Figure 3) illustrates how important it is for CS students to comprehend the code in detail. In this case, students would need to develop an understanding of numerical errors in floating-point computation [68]. Although prior theory suggests how to sequence the development of code comprehension skills in relation to manual code-writing and other programming skills [10], it may be necessary to reexamine this theory for introductory courses that introduce code-writing using LLMs [61]. For instance, instructors have expressed concerns that the mental models constructed by students who rely excessively on LLMs may be fragile [41, 50], hinder the development of crucial metacognitive skills [55], limit learning [24], and eventually lead to an over-reliance on such tools [28, 29]. Indeed, students [54, 61] and the creators of such tools [14] have expressed similar misgivings. At the same time, if exposure to these tools is delayed, students may develop a false sense of confidence in these tools [21] and may later fail to develop essential skills such as debugging [35].

## 6 Conclusion
Given the widespread availability of LLMs that can generate code that is plausible but not necessarily correct, prior work has emphasized the importance of helping students develop two complex skills: code comprehension and proactive task comprehension. Our study anticipates the creation and availability of powerful systems that will continue the trend of simplifying programming-related tasks [9]. We show that non-CS majors may be able to leverage LLMs to develop reasonably accurate code using reactive task comprehension, a skill that is (currently) challenging for LLMs but (comparatively) easier for humans. However, for CS majors, our study suggests that students must develop the ability to comprehend code and recognize potential ambiguities in task specifications. We leave an interesting question unanswered: Is proactive task comprehension still an important skill for CS students to develop?
